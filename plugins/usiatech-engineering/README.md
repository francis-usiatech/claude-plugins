# UsiaTech Engineering (`usiatech-engineering`)

Shared engineering workflow **and governance** for UsiaTech repositories (WaypointCareer, HEI Impact Intelligence). Project rules stay in each repo's `AGENTS.md`. This plugin supplies the procedures, reviewers and guard that are the same everywhere.

## Components

| Type | Name | What it does |
|---|---|---|
| Skill | `verify` | Runs the repo's definition-of-done gate (from `.claude/engineering.json` or AGENTS.md) and reports PASS/FAIL; checks the active plan's acceptance criteria against evidence from this session (unshown criteria warn, they don't fail the gate) |
| Skill | `release` | Scoped staging → verify → reviewers → one conventional commit → PR → merge → `DDMMMYYYY-XX` tag → branch cleanup |
| Skill | `user-guide-update` | Finds and updates affected user-guide pages and the changelog |
| Skill | `setup-engineering` | Creates `.claude/engineering.json` for a repo and checks the AGENTS.md/CLAUDE.md layout |
| Skill | `approve-plan` | Routes work small (plan directly) or large (`clarify` → `to-spec` → `to-tickets` first); records the approved plan with a pre-plan checklist, acceptance criteria and tasks as the scope baseline (`.claude/plans/active.md`) after a governance pre-flight; updates it on approved scope changes; archives it when done |
| Skill | `tdd` | Test-first cycles (red → green → refactor) with the failing and passing evidence for each cycle, then the verify gate |
| Skill | `debug` | Root cause before fix: reproduce → localize (hypotheses, bisect) → reduce → approved fix via `tdd` → regression guard test |
| Skill | `mutation-test` | Breaks the change's fix points one at a time from a mutation list Claude writes, using the shipped `mutation-runner.mjs`; reports each surviving mutation as a missing test and asks whether to add one. On demand, never a gate |
| Skill | `clarify` | One question at a time until purpose, success, constraints and scope edges are clear; ends with an understanding note the user corrects. Writes no files |
| Skill | `to-spec` | Writes the confirmed understanding to `docs/specs/YYYY-MM-DD-<slug>.md`: requirements R1…, measurable acceptance criteria AC1…, open questions answered or deferred before approval |
| Skill | `to-tickets` | Splits an approved spec into small tickets (covers R/AC, blocked by, done when); files GitHub issues after one confirmation, or writes a Tickets section into the spec without `gh` |
| Agent | `governance-reviewer` | Read-only gate: traces every change to a requirement, flags out-of-plan work, ADR/rule violations and dangerous actions; verdict PASS/FLAG/BLOCK |
| Agent | `convention-reviewer` | Read-only review of a diff against the repo's root and folder AGENTS.md |
| Agent | `silent-failure-reviewer` | Read-only review for swallowed errors, masking fallbacks, lost async errors, ignored exit codes and tests that can't fail |
| Agent | `security-reviewer` | Read-only security review of a diff: injection, access control, input handling, secrets, SSRF/path traversal, crypto, dependencies and CI workflows |
| Agent | `workflow-reviewer` | Read-only review of `.github/workflows/` changes: privileged triggers running PR code, script and prompt injection, exposed secrets, pinning and token permissions; judges the `wf-*` rule findings |
| Agent | `supply-chain-reviewer` | Read-only review of `package.json` and lockfile changes: typosquats and dependency confusion, advisories, install scripts, deprecated or stale packages, lockfile drift and widened ranges; judges the `sc-*` rule findings and lookup fail-opens |
| Hook | Governance guard (PreToolUse on Bash + edits) | **Deny:** catastrophic or rule-breaking actions and edits that write secrets. **Ask:** risky commands, likely hard-coded credentials, high-risk workflow or dependency content, governance/CI/dependency files, edits outside the approved plan. **Log:** every decision, workflow and dependency finding, and failed dependency lookup to `.claude/governance-log.jsonl` |
| Hook | After-Bash workflow check (PostToolUse and PostToolUseFailure on Bash) | Runs the workflow content checks on every `.github/workflows/*.yml` file a Bash command added or changed (on disk, staged or committed), shows high-risk findings at once and logs every finding. See "After-Bash workflow check" below |

### Mutation testing
`mutation-test` runs `skills/mutation-test/mutation-runner.mjs` from the plugin (it isn't copied into the repo; Node built-ins only). The list is JSON: `{ "timeoutMs"?, "mutations": [{ "label", "file", "find", "replace", "command", "timeoutMs"? }] }`, with `file` relative to the repo root and `find` occurring exactly once. The runner runs each distinct command unmutated first (with the largest `timeoutMs` of the entries that share it), then applies one mutation at a time and restores the file from its original bytes after each one, on error and on interrupt (CRLF preserved; `find` is matched on bytes, so a file that isn't UTF-8 is never re-encoded). `timeoutMs` is a whole number from 1 to 2147483647. It never stages or commits. Each mutation is reported as `CAUGHT` (tests failed), `SURVIVED` (tests passed: a missing test), `NOT-FOUND` (`find` matched 0 or 2+ times), `TIMEOUT` (process tree killed) or `ERROR` (the file couldn't be read or written, the command was killed by a signal, its process tree couldn't be killed and it didn't close within 2 s, or the run was interrupted). Exit codes: 0 when the run completes (survivors never block), 1 when the baseline failed and nothing was mutated, 2 for an invalid list (including paths into `.git` or out of the repo, directly or through a link) or no git repo, 3 when a restore failed (the file is named and its original bytes saved to a temp file) or the file changed while its command ran (it is left as it is, not overwritten, and its current bytes are saved too), 130 when interrupted. The runner prints every distinct command before running any; the skill has the user confirm them first, because they run through the shell. `release` suggests it when a diff touches rule, check, policy or guard code.

### Gate runner
`verify` runs the gate through `skills/verify/gate.mjs` from the plugin (ESP-44; it isn't copied into the repo; Node built-ins only) when `.claude/engineering.json` has a `verify` list. Run it by hand from anywhere in the repo with `node <plugin>/skills/verify/gate.mjs`.
- **What it runs:** the `verify` steps in order, then the `verifyConditional` steps whose `when` prefix matches a changed file (the diff against `HEAD` plus untracked files), then the fake-pass check. It stops at the first failing step.
- **Timeout:** a step that runs past its timeout is stopped, with every process it started (the whole process tree on Windows, the process group elsewhere), and fails the gate. The timeout is the step's own `"timeoutMs"` in `.claude/engineering.json`, or 10 minutes; the fake-pass check gets 10 minutes. An interrupt (Ctrl+C, or the terminal closing) stops the running step the same way and fails the gate. The CI gate (`run-verify.mjs`) does not read `timeoutMs`.
- **What it prints:** one line per step, `PASS  <name> (exit 0, 12 s)`, `FAIL  <name> (exit 3, 2 s)`, `FAIL  <name> (timed out after 600000 ms, 600 s)`, `NOT RUN  <name>`, or `SKIPPED  <name> (no changed file under src/)` for a conditional step that wasn't selected; the last 40 lines of a failing step; every fake-pass finding; then `Log:`, `Gate run:` with a UTC timestamp, and `Gate: PASS` or `Gate: FAIL`. The last line and the exit code are the verdict; a step's own output can't change them. Don't pipe or filter it: the output is already short.
- **Exit codes:** 0 when the gate passed; 1 when a step or the fake-pass check failed (a fake-pass check that couldn't run counts as failed); 2 when the gate could not start or finish: no usable `verify` list, a step it can't accept, git can't list the changed files, or the log can't be written.
- **Steps it rejects (exit 2):** a step without a `name` and `run` string; a `name` with control characters or the name `fake-pass check`; a `run` with a line break or another control character (`cmd.exe` would run only its first line); a `timeoutMs` that is not a whole number from 1 to 2147483647; a conditional step whose `when` is missing, empty, or holds a prefix with a backslash, a leading `./` or `/`, a `..` segment, a control character, or a space at either end. Prefixes are relative to the repo root with forward slashes, such as `src/`, and match exactly, case included.
- **Log:** each step's full output goes to `gate.log` in a new folder `<OS temp folder>/usiatech-gate-<random>`, never into the repo. The folder is private to the user (step output can hold secrets). Old logs aren't removed.
- **Limits:** it doesn't honour `expectNoDiff` (the CI gate does), has no timeout for the gate as a whole and no way to change the 10-minute default, ignores config keys it doesn't know (a misspelt `verifyConditional` runs nothing), and doesn't read test counts out of a step's output. A repo with no `verify` list keeps the `AGENTS.md` path, where `verify` runs the commands one at a time.

## Per-repo configuration: `.claude/engineering.json`
Start from `templates/engineering.json` (or run the `setup-engineering` skill).

| Key | Purpose |
|---|---|
| `verify` | Commands always run by `verify`, in order. A step may carry `"timeoutMs"` (see "Gate runner"; default 10 minutes) |
| `verifyConditional` | Extra commands run only when changed files start with a `when` prefix |
| `git` | Base/release branch, tag format, commit style |
| `protectedPaths` | Globs the agent may never edit |
| `immutableWhenCommitted` | Globs editable only until committed (e.g. migrations) |
| `allowEnvExample` | Allow edits to `.env.example` (default `true`) |
| `userGuide` | Guide folder, changelog file, optional manifest |
| `reviewers` | Agents `release` runs before committing, in two stages: `governance-reviewer` first, then the rest in parallel, or both stages together on a small diff inside the plan (default adds `convention-reviewer`, `silent-failure-reviewer`, `security-reviewer`; repo-specific ones allowed). Each PR gets one full review round, and on a docs-only diff two reviewers are skipped and `convention-reviewer` runs on Sonnet (rules in the `release` skill) |
| `decisions` | How `approve-plan` and `release` ask for decisions. `batch` (default `true`) puts every open decision at pre-flight and at release review into one question with a recommended default; `false` asks about each one on its own. `nitsNeedDecision` (default `false`) means nits listed in the PR need no decision; `true` asks about each nit. A non-boolean value is reported once as an advisory config problem (see "Config problems" below) and counts as the default. Older guards ignore the `decisions` key |
| `planning` | How `approve-plan` plans. `preflightReviewers` (default none) is a list of `{ "agent": "<name>", "when": ["<prefix>", …] }` entries: extra agents that `approve-plan` runs on the draft plan in design mode, in parallel with `governance-reviewer`. An entry with `when` runs only when a prefix matches the start of a path in the plan's **Files** section (same prefix rules as `verifyConditional.when`); one without `when` always runs. Their `BLOCK`s must be fixed, and their `FLAG`s join the one batched pre-flight question, each labelled with the reviewer that raised it. A reviewer that fails or isn't installed is reported by name and doesn't count as a pass. A bad value is reported once as an advisory config problem (see "Config problems" below), and `approve-plan` skips an invalid entry and names it by its index, never by its `agent` value. A pre-flight reviewer receives only the draft plan. Older guards ignore the `planning` key |
| `governance` | `protectedBranches`, `askPaths`, `requirePlan`, extra `denyCommands` / `askCommands` (regex + reason), `allowlist` (see below), `trustedWritePaths` and `planEdits` (`"allow"`, `"ask"` or `"all"`; see "Trusted writes" below), `rulesFile` |
| `tickets` | Ticket tracker for `to-tickets`, `approve-plan` and `release`. `tracker` is `"github"` (default when the section is missing) or `"jira"`; see "Jira tracker" below |

### Jira tracker
With `tickets.tracker` set to `"jira"`, the skills file and move tickets in Jira through `scripts/jira-tracker.mjs` (no dependencies; the decision is [ADR 0003](../../docs/adr/0003-jira-ticket-tracker.md)):

```json
"tickets": {
  "tracker": "jira",
  "jira": {
    "site": "https://example.atlassian.net",
    "project": "ESP",
    "issueType": "Subtask",
    "parent": "ESP-27",
    "statuses": { "started": "In Progress", "verified": "In Testing", "merged": "Ready for Release", "released": "Released" }
  }
}
```

- **Keys.** `site` (https, host only: no path, port, user name, password, query or fragment), `project` (upper-case key), `issueType` are required; `parent` is optional. Each `statuses` event is optional, and an event with no status is skipped. An invalid value for a known key makes the whole section unusable, and `node <plugin>/scripts/jira-tracker.mjs check`, run from the repo root, names it (it reads the config only and sends nothing). Unknown keys (other than `$comment`) in `tickets`, `tickets.jira` and `statuses` are reported the same way, so a misspelled `statuses` or `tracker` is caught.
- **Environment.** `JIRA_EMAIL` and `JIRA_API_TOKEN` (an Atlassian API token) are required and read only from the environment, never from config or files. The token is sent only to a site ending in `.atlassian.net`, or to the host of `JIRA_SITE` when that is set. Set `JIRA_SITE` to your own site to pin the host: without it, any Atlassian tenant named in the config is accepted. `check` reads no environment, so for a site outside `.atlassian.net` it prints a warning on stderr (exit 0) that Jira commands will refuse it unless `JIRA_SITE` is set to it. A token of 16 characters or more is replaced by `***` if it appears in the output, and so is the Basic credential built from it. Body and messages files must be UTF-8; a UTF-16 file (from a PowerShell 5.1 redirect) is refused with exit 2.
- **What the skills do.**
  - `to-tickets` files each ticket in blocker order, links Blocks between them and writes each key to the spec's Tickets section.
  - `approve-plan` moves the keys named by the plan's tasks to `started`.
  - `verify` moves the keys named by the plan's tasks to `verified` when the gate passes and every acceptance criterion is shown.
  - `release` moves them to `merged` with a PR-link comment when the PR merges, and moves every key in the commit messages since the previous tag to `released` after showing you the list.
  - `clarify` and `approve-plan` accept a Jira key (e.g. `ESP-24`) as a requirement reference.
- **Failures.** Nothing is retried. A missing credential, network error, timeout, 4xx/5xx response or a status with no matching transition exits non-zero with the issue and cause; a config or argument problem exits 2. `to-tickets` stops on the first failure and reports what was and wasn't created (a timed-out create is "unknown, may exist"). In `release`, git steps are never undone by a Jira failure; each failed transition is reported for you to fix in Jira.

## Governance model (layered)

| Layer | Mechanism | Effect |
|---|---|---|
| 1. Before work | `approve-plan` + `governance-reviewer` pre-flight | Plan must cite requirements. Scope is recorded. |
| 2. During work | Governance guard hook | Denies catastrophic actions. Asks on risky or out-of-plan actions. Logs everything. |
| 3. Before commit | `governance-reviewer` (+ `convention-reviewer`) in `release` | `BLOCK` stops the commit. `FLAG` needs the user's decision. |
| 4. Pull requests (CI) | `templates/github/` → `.github/` + repo `REVIEW.md` | Every PR runs these jobs (details below). `governance-gate` is the required check. |
| 5. After | Archived plans + `governance-log.jsonl` + PR verdict comments | Audit trail of scope and approvals |

**PR governance jobs:**
- `governance-checks` (deterministic):
  - requirement reference present in the PR description
  - branch flow (only `develop` or `hotfix/*` into `main`)
  - no `.env` files, no edits to committed immutable files (a type change, such as turning one into a symlink, counts as an edit)
  - governance/CI/dependency changes need the approval label (`governance.approvalLabel`, default `governance-approved`); a rename counts at both ends, so moving such a file out of its folder needs it too
  - workflow content checks on each changed `.github/workflows/*.yml` (below): high-risk findings fail unless labelled; warnings are listed
  - dependency checks on each changed `package.json` and lockfile (below): the same tiers, and a failed npm lookup fails the job even with the label
  - gitleaks secrets scan
- `verify-gate`: the same `.claude/engineering.json` gate as the local `verify` skill.
- `ai-governance-review`: Claude Code GitHub Action applies `REVIEW.md` + AGENTS.md + `governance.md` + intent/ADRs. It returns a structured PASS/FLAG/BLOCK verdict, posts inline comments, and keeps one verdict comment per commit.
- `governance-gate` (required check): fails on failed checks or verify, on BLOCK or ERROR, on FLAG without the label, or when there's no verdict for the head commit. A skipped AI review needs no verdict only for an opt-out (`GOVERNANCE_AI_REVIEW=off`, in any case), a draft or a fork PR. When an edit or label event skips the review, the gate still needs the head commit's verdict from an earlier run. The gate reads a verdict only from a bot comment that starts with post-verdict's `<!-- governance-review -->` line and ends with the verdict marker, and the verdict comment escapes `<` in the AI text, so neither the AI text nor another bot comment that quotes one can forge a verdict. (A workflow that posts PR text word for word as `github-actions[bot]` could still copy both lines.)

Scripts and rules are read from the **base branch** (`_gov/`), so a PR can't change the checks it is judged by. The workflow file itself is the exception: GitHub runs `pr-governance.yml` from the PR, so a PR that edits it can change or skip the gate. The checks flag such edits (`.github/**` needs the approval label), but a required status check alone does not stop them: the edited workflow can still report a passing `governance-gate`. To enforce it, require Code Owner review on `.github/**` (the ruleset in `templates/ruleset-governance.json`, which `setup-engineering` applies after you approve), or use an org ruleset with **Require workflows to pass** pointing at the base-branch workflow. The PR description is passed to the reviewer as untrusted data.

The AI review job runs with `--setting-sources user`, so a PR's own `.claude/settings.json` hooks, plugins and `.mcp.json` are not loaded. It has no Bash tool: the diff (as text, so `.gitattributes` can't hide a file) and commit list are written to `.pr-diff.patch` and `.pr-log.txt` before it starts, and base versions of files come from `_gov/`. As defence in depth against a prompt-injected reviewer, its checkouts don't persist the token and it can't read `/proc`, the runner's temp and install folders, the workspace `.git/` folder (the action writes its token into the remote URL), or credential folders in the home folder (`~/.claude`, `~/.config`, `~/.ssh`, `~/.docker`); the workspace itself sits under the home folder, so the home folder as a whole stays readable, alongside the main defence that fork PRs get no AI review (below). A solo owner keeps Code Owner review on and merges with the ruleset's admin bypass, which GitHub records per PR. `claude-code-action` is pinned to a commit and the gitleaks image to a digest; bump both on purpose. Fork PRs get no AI review (secrets are withheld), so they fail the gate until a maintainer re-opens them from a branch.

**Default guard rules** (on Bash and PowerShell commands, and on Edit, MultiEdit, Write and NotebookEdit)
- **Deny:**
  - a recursive forced delete (`rm`, `Remove-Item`, `ri`, `rd`, `rmdir`, with `-` flags clustered, separate or long) of root, home or the workspace
  - `curl … | sh`
  - `--no-verify` or any abbreviation git accepts (`--no-veri`), `git commit -n`, and any command naming `core.hooksPath` (reads included)
  - `mkfs`/`dd` to devices
  - `DROP DATABASE`/`SCHEMA`
  - shutdown/reboot
  - `chmod -R 777`
  - editing `.env*`, protected paths or committed immutable files
  - edits whose content contains a private key or a provider API key/token (AWS, GitHub, Anthropic, OpenAI, Stripe live, Google, Slack); documented placeholders are ignored
- **Ask:**
  - force push; mirror push; reset/clean/restore, `checkout -f`/`switch -f`; branch deletion (local or remote, `-d` or `--delete`); history rewrite; a recursive delete (`rm -r`, `rm --recursive`, `Remove-Item -Recurse`). Abbreviations of `reset --hard`, `clean --force`, `checkout --force` and `push --delete`/`--mirror` count (`reset --har`).
  - `DROP TABLE`/`TRUNCATE`/unfiltered `DELETE`; weakening RLS; DB reset
  - dependency adds; publish; ssh/scp/rsync/terraform/kubectl/ansible/firebase deploy/docker prune
  - reading `.env`; `sudo`; `chmod 777`
  - commits or merges on protected branches, and pushes to them
  - edits to `.claude/**`, AGENTS.md, CLAUDE.md, REVIEW.md, `.github/**`, `package.json`
  - edits that look like a hard-coded credential (`password = "…"`, `apiKey: "…"`)
  - edits outside the approved plan, and edits to the plan itself (`.claude/plans/active.md`) that change more than evidence, task ticks or the change log (see "Trusted writes" below)
  - edits outside the project folder, except the trusted write paths below
  - any action while `.claude/engineering.json` has an escalating config problem, such as malformed JSON or an invalid command pattern (default deny rules still apply; see "Config problems" below)
- **Limits:** the rules match command text, so a command built at run time (a variable, an alias, `Invoke-Expression`) can get past them. MCP tools that write files or push (such as a GitHub `push_files`) are not guarded. Not matched yet: cmd-style `/s` flags (`rd /s /q`), the `del`/`erase` aliases, `git branch --d`, and Windows drive-root targets (`C:\`), which are only asked.
- On Windows every path check treats a name with trailing dots or spaces or an alternate data stream (`.env::$DATA`, `AGENTS.md:stream`) as the file it writes; the log keeps the name as written.

**Workflow content checks** (`templates/github/scripts/workflow-rules.mjs`). The guard runs them on the post-edit content of any `.github/workflows/*.yml` edit, the after-Bash check on any workflow a Bash command changed, and `governance-checks` on each changed workflow in a PR. All compare against the previous version: the file on disk (or in git) locally, the base-branch file in CI. A file renamed into `.github/workflows/` from a non-workflow path is checked in CI as a new workflow, not compared with the old file. On Windows the guard also treats a path with trailing dots or spaces or an alternate data stream (`x.yml.`, `x.yml `, `x.yml::$DATA`, `x.yml:stream`) as the workflow it names, as it does for every path check; on POSIX these are ordinary names.

| Rule | Tier | Catches |
|---|---|---|
| `wf-privileged-checkout` | high | `pull_request_target` / `workflow_run` / `issue_comment` jobs that check out PR-controlled code: `actions/checkout` with a PR ref or a ref or repository taken from a step output (`${{ steps.pr.outputs.sha }}`), or a `run:` step that gets the PR head with `git clone --branch`, `git fetch` / `pull` then `checkout` / `switch` (also after global options such as `git -C dir`), or `gh pr checkout` |
| `wf-privileged-secrets` | high | secrets in such a job, including a job that calls a reusable workflow with `secrets: inherit` (the called workflow can't be read, so this fails closed) |
| `wf-untrusted-input` | high | untrusted event text (`github.event.*` titles, bodies, branch names, commit messages, `github.head_ref`), or a whole event object such as `toJSON(github.event)` or `join(github.event.issue.*)`, in `run:`, an `actions/github-script` script, or an AI action's inputs. The same goes for `${{ env.NAME }}` when `NAME` is set from such text in a workflow, job or step `env:` (a lower level's value replaces a higher one's, but not a name its own block set from such text; `toJSON(env)`, `env.*` and `env[…]` count when any name is untrusted). Every env name counts as untrusted after a whole-expression `env:` block that reads such text, or a name outside `[A-Za-z0-9_-]` set from it. A `run:` step that writes such text (or names such an env name in any shell syntax: `$T`, `$env:T`, `%T%`) to `$GITHUB_ENV` makes every later `${{ env.* }}` in the job untrusted, and one that writes it to `$GITHUB_OUTPUT` makes `${{ steps.<id>.outputs.* }}` untrusted; outputs set by other actions aren't followed. `$NAME` read by the shell is safe. Expressions are matched in any case, spacing or `['key']` notation. A computed index anywhere on a `github` path (`github.event[format(...)]`, `github.event[inputs.key]`) counts as untrusted, whatever field follows; closed string literals such as `'github[bot]'` don't |
| `wf-unparsed` | high | parts of the file the checks can't read: YAML anchors, aliases, merge keys, tags or explicit keys; a double-quoted escape that isn't valid YAML 1.2 (every YAML 1.2 escape is decoded, `\x24` to `$` included, and the decoded text is checked), or one that gives a surrogate or a code point above U+10FFFF; quoted strings or `[ ]` / `{ }` collections that span lines, and quotes or brackets that never close; a `key: value` pair inside a flow sequence, a plain flow-mapping key whose `:` is directly followed by a quote, or a non-string entry in an `on` list (forms GitHub may read differently, evidence on #13); a raw U+0085, U+2028 or U+2029; `jobs`, a job, `steps` or a step of the wrong type; lines the parser skipped; or (in the guard) an edit whose result can't be worked out. The checks fail closed rather than pass a file they only partly read |
| `wf-unpinned-action` | warning | third-party actions and reusable workflows not pinned to a 40-character SHA (`actions/*`, `github/*` and local actions exempt) |
| `wf-write-all` | warning | `permissions: write-all` |
| `wf-permissions-widened` | warning | a scope that grows compared with the previous version, or an explicit `permissions` block that is removed. A previous version that can't be fully read counts as granting no permissions, and the warning says so |
| `wf-allowlist-ignored` | warning | a `governance.allowlist` entry for a `wf-*` rule that suppresses nothing (see the allowlist rule below) |

High-risk findings make the guard ask, even when the path isn't in `askPaths`, and fail the CI checks unless the PR has the approval label. Warnings never block. Every finding is logged as `"decision": "finding"` with `rule`, `tier`, `file`, `line` and `detail`, and `governance-reviewer` counts them. The existing label requirement for `.github/**` changes is unchanged. The new checks add to it; they don't replace it.

**After-Bash workflow check** (`hooks/scripts/bash-workflow-check.mjs`). A workflow written by a Bash or PowerShell command (a heredoc, `cp`, `sed -i`, or `git` alone) gets the same checks as one written with Edit. Before each such call it doesn't deny, the guard snapshots the workflow files, the git index and HEAD, branches and tags, keyed by the call's `tool_use_id`. After the call (on `PostToolUse`, and on `PostToolUseFailure` when the command failed), the hook runs the workflow rules on every workflow file that changed: on disk, in the index, or in a branch, tag or HEAD the command moved or created, so with a usable snapshot a workflow staged or committed without touching the files on disk is caught too. The command has already run, so nothing is blocked: high-risk findings are shown to Claude and the user at once, and every finding is logged as for an edit. A command that changes no workflow file loads no rules module and, in a git repo, costs 4 git commands (2 in the guard, 2 in the hook).
- Snapshots live in `$TMP/usiatech-governance/{project}/`, outside the default trusted write paths. A `trustedWritePaths` entry in that folder is a config problem, since Claude could otherwise rewrite a snapshot without a prompt. On POSIX they are written owner-only; on Windows the per-user temp folder protects them. A snapshot is trusted only when every git id in it is a full hex SHA and its folder is a real folder (not a link) that, on POSIX, the user owns and no one else can write to. Every git id or path taken from a snapshot is passed after `--end-of-options`. The guard asks before a Bash command that names `usiatech-governance` or `bash-wf-`.
- With no usable snapshot (missing, unreadable or refused, which is logged), the hook checks the workflow files that differ from HEAD on disk or in the index, untracked and git-ignored ones included, against HEAD.
- Internal errors fail open and are logged as `"decision": "error"`, like the guard. A hook that Claude Code stops at its 10 s timeout logs nothing. Needs git 2.24 or later (`--end-of-options`); with older git the hook fails open and logs it.
- **Known limitations:**
  - a background Bash command (`run_in_background`) isn't checked: the hook fires at launch, before it writes anything, and logs that it skipped the check;
  - a command can still rewrite its own snapshot through a path the guard's ask doesn't match, and so hide a change (the snapshot checks only stop it passing options to git);
  - a workflow pushed from a commit no local branch, tag or HEAD points to (`git commit-tree` pushed as `<sha>:refs/heads/x`, or a push to a URL) isn't seen, because remote-tracking refs aren't watched (#63);
  - with no usable snapshot, a workflow the command committed isn't seen, because only differences from the new HEAD are checked. This includes a shared POSIX `/tmp` where another user created `usiatech-governance` first, which makes every call fall back.

  CI checks every workflow a PR changes, so it still catches all four.

**Dependency checks** (`templates/github/scripts/supply-chain-rules.mjs` and `supply-chain-lookups.mjs`). The guard runs them on the post-edit content of any `package.json`, `package-lock.json` (v1–v3), `pnpm-lock.yaml` (v5–v9) or `yarn.lock` (classic and berry) edit outside `node_modules/`, and `governance-checks` runs them on each changed one in a PR, against the previous version. Only added or changed entries are checked. On Windows the guard treats `package.json.`, `package.json::$DATA` and the same variants of the lockfiles as the file they name, as it does for workflows.

| Rule | Tier | Catches |
|---|---|---|
| `sc-typosquat` | high | an added unscoped name of 5+ characters one edit (insertion, deletion, substitution or swap) away from a bundled list of about 200 popular packages, e.g. `expresss`, `lodahs` |
| `sc-advisory` | high / warning | a known npm advisory for the added or changed version: critical or high is high risk, moderate or low a warning |
| `sc-resolved` | high / warning | a new or changed lockfile entry downloaded from outside `registry.npmjs.org` / `registry.yarnpkg.com` (https), or from a registry tarball that isn't `<name>/-/<name>-<version>.tgz` for that entry, is high risk; a changed download or checksum for an unchanged version is a warning. Local sources count as outside the registry: a pnpm `type: directory` resolution is reported as `file:<directory>`, and a yarn berry locator other than `npm:` or `patch:` (`file:`, `https:`, git) as the locator itself. Private registries need an allowlist entry |
| `sc-unparsed` | high | a manifest or lockfile the parser can't read. `pnpm-lock.yaml` and `yarn.lock` are read only in the layout pnpm and yarn write, so any other spelling is unread: quoted or spaced keys (`"packages":`, `packages :`), a repeated key or field, fields at another indentation, a value on the lines below any field other than the block fields pnpm and yarn write (`dependencies`, `engines`, `bin` and the like), so `name`, `version` and `resolution` must be on one line, a pnpm `resolution` that isn't a one-line `{key: value}` map, pnpm `name:` / `version:` fields that disagree with the key, a registry version (a pnpm key or `version:` field, a yarn berry `npm:` locator) that isn't an exact semver version, which rules out `::__archiveUrl=` suffixes, a pnpm git, URL or file package with no `tarball`, `repo` or `directory` source, an unknown pnpm resolution `type`, a yarn berry `resolution` (or the `npm:` locator inside a `patch:` one) whose version disagrees with `version:`, a double-quoted name, version, source or checksum holding a `\` escape, a yarn field the lockfile's format doesn't write (such as `resolved` in berry or `resolution` in classic; a classic `name` field is read as the installed package, so it gives `sc-alias`), a `__metadata` key other than berry's exact header, a yarn descriptor it can't read anywhere in an entry's key (`__metadata` among them), an `npm:` alias in any descriptor that asks for a different package from the entry's, a `package-lock.json` whose `packages` or `dependencies` is there but not an object, a pnpm `lockfileVersion` that isn't a number, a NEL, LS or PS line break, or a pnpm or yarn berry entry without a `resolution`. pnpm 10 `type: variations` resolutions are not read yet. Yarn berry entries are skipped as the project's own folders only when their `resolution` is a `workspace:`, `link:` or `portal:` locator. A lone CR counts as a line break, as it does for YAML and yarn. Also (in the guard) an edit whose result can't be worked out; nothing in it was checked |
| `sc-alias` | warning | a lockfile entry that installs under one name but fetches another package (`node_modules/lodash` holding `evil-pkg`, an `npm:` alias, a yarn berry `resolution` naming another package, or any yarn descriptor in an entry's key naming a package other than the one it fetches, such as `evil-pkg@^1, lodash@^4:`), unless the base had the same alias |
| `sc-install-script` | warning | the version has a `preinstall`, `install` or `postinstall` script |
| `sc-deprecated` | warning | the version is deprecated on the registry |
| `sc-stale` | warning | the package's latest release is more than 2 years old, or the registry gives no readable release date |
| `sc-not-found` | warning | the registry doesn't know the name (possible dependency confusion) |
| `sc-non-registry` | warning | a `workspace:`, `file:`, `link:`, git, URL or `npm:` alias specifier; it isn't looked up |
| `sc-lockfile-drift` | warning | a lockfile changes without its `package.json` (in the guard, any lockfile edit on its own) |
| `sc-range-widened` | warning | a range that widens to `*`, `latest`, `x` or `>=` |

The advisory, install-script, deprecated, stale and not-found checks look packages up on `registry.npmjs.org` (keyless; package names and versions are sent there, as `npm audit` does). Registry lookups cover direct dependencies added in a manifest, and find the latest version of an entry changed to an open range, 8 at a time; advisories cover every added or changed entry in one request. A manifest range is looked up at the version its lockfile pins in the same change. In the guard, all lookups share a 6 s deadline and a failed or timed-out lookup **fails open**: the offline findings stand and one `"decision": "error"` entry naming the lookup is logged. In CI each request has 20 s and the whole run 120 s, and a failed lookup **fails closed** with "Dependency lookup unavailable". See [ADR 0001](../../docs/adr/0001-guard-network-lookups.md).

**Test content checks** (`templates/github/scripts/fake-pass-rules.mjs`). These catch tests that make a run green without proving anything. The `verify` skill runs them once its commands pass, through `fake-pass-check.mjs`, on the changed files it sees (`git diff HEAD` plus untracked files), from the repo root even when run from a subdirectory. `governance-checks` runs them on each JS/TS file a PR adds, changes, renames or copies. Both read changed files in full. Test files (`*.test.*`, `*.spec.*`, `__tests__/`, `test/`, `tests/`) get every rule. Other JS/TS files get only `fp-placeholder`. An unsuppressed high finding makes verify report **Gate: FAIL** and fails the CI checks unless the PR has the approval label ([ADR 0002](../../docs/adr/0002-fake-pass-checks-fail-the-gate.md)).

| Rule | Tier | Catches |
|---|---|---|
| `fp-only` | high | a focused test or suite (`.only` on `it`, `test`, `describe`, `suite` or `context`, also in a modifier chain such as `it.only.each` or `test.concurrent.only`, which may be split across lines, or `fit` / `fdescribe`), which runs alone and silently drops the rest of the suite |
| `fp-skip` | high | a skipped or pending test (`.skip`, `.todo` or `.fixme` on the same names, vitest's conditional `.skipIf(…)` / `.runIf(…)`, also in a modifier chain such as `it.skip.each`, `xit`, `xtest`, `xdescribe`, `xcontext`, or a node:test `{ skip }` / `{ todo }` option other than `false`), which passes without running |
| `fp-empty-test` | high | a test whose body is empty |
| `fp-no-assert` | high | a test with no recognised assertion: `assert`, `t.assert`, `expect(`, `.should` or `t.plan(`. A test that asserts only through a helper is reported; allowlist it, or assert in the test itself |
| `fp-unreadable` | high | a test file the checks can't read: one git or the file system can't return (or that isn't a regular file, such as a symlink, locally and in CI), one over 1,000,000 characters, or one with a comment, string or template that never closes. The checks fail closed rather than pass a file they only partly read |
| `fp-placeholder` | warning | `TODO`, `FIXME`, `XXX` (upper case) or "not implemented" left in a changed JS/TS file |

The checks are pattern based, with comments, strings and regex literals blanked out first, so `'skip'` in a message doesn't match. There's no parser and no dependency. Known limits: aliases (`const o = it.only`), computed access (`it['only']`) and conditional calls (`(c ? it.skip : it)(…)`) aren't detected. Unchanged files are never scanned, so existing debt shows up only when a file is next changed. To accept a finding, allowlist it with a reason, for example `{ "rule": "fp-no-assert", "path": "tests/helpers-assert.test.mjs", "reason": "assertions live in a helper" }`. `verify` reads the allowlist from the working tree. CI reads it from the base branch.

To accept a known finding, add an entry to `governance.allowlist`: `{ "rule": "wf-unpinned-action", "path": ".github/workflows/pr-governance.yml", "reason": "…" }`, or for a package `{ "rule": "sc-install-script", "package": "esbuild", "reason": "…" }`. Each entry needs a rule ID plus a `path` glob or a `package` name, so a rule can't be turned off everywhere; a path made only of wildcards (`**`, `*`, `**/*`) is rejected. An entry for a workflow rule (`wf-*`) suppresses only when its `path` names one literal file (no `*`, `?`, `[` or `{`) and its rule isn't `wf-unparsed`. Any other `wf-*` entry (a glob path, `wf-unparsed`, or a `package` only) stays valid but suppresses nothing, and gives a `wf-allowlist-ignored` warning naming the entry, in the guard on workflow edits, in the after-Bash check, and in CI once per run when workflows changed. From 0.10.0 this means a broad entry such as `.github/workflows/*` no longer suppresses: list each workflow file instead. Allowlisted findings are still reported and logged as `suppressed`, but they don't block. CI reads the allowlist from the base branch, so a PR can't allowlist its own findings. The template's allowlist ships empty. The shipped `pr-governance.yml` gets one warning (`anthropics/claude-code-action@v1` is on a major tag): pin it to a SHA, or allowlist it with a reason as shown above.

All default rules live in one module, `templates/github/scripts/governance-rules.mjs`. The guard hook imports the plugin's copy. `setup-engineering` copies it into `.github/scripts/` with the CI scripts, which read the repo's copy. The two match at install time. After upgrading the plugin, re-copy `templates/github/scripts/` or the PR checks keep the older rules (from 0.9.0 the fake-pass checks need `fake-pass-rules.mjs` and the updated `governance-checks.mjs`; 0.10.0 updates `workflow-rules.mjs`, `governance-rules.mjs` and `governance-checks.mjs`).

Path checks ignore case on Windows and macOS (`.ENV` is treated as `.env`), and CI always ignores case. A config value of the wrong type (e.g. a string where a list is expected) is reported as a config problem; what the guard then does depends on the key (see "Config problems" below). The CI checks (`governance-checks`) fail with the problem named, so a broken base-branch config can't pass a PR.

**Config problems** (ESP-35). What the guard does with a problem in `.claude/engineering.json` depends on the key:
- **Escalating**: dropping the value could weaken the guard, so every action that isn't denied becomes a confirmation prompt until the file is fixed. The prompt names every problem, advisory ones included. These escalate:
  - a file that can't be parsed or isn't an object;
  - a `governance` that isn't an object;
  - a bad `governance.askPaths`, `governance.protectedBranches`, `governance.denyCommands` or `governance.askCommands` (the list or an entry);
  - a bad `git` or `git.releaseBranch`;
  - a bad `protectedPaths` or `immutableWhenCommitted`.
- **Advisory**: the guard doesn't read the key, or the bad value is dropped or replaced in a way that only makes the guard stricter, so the problem itself never causes a prompt. These are advisory:
  - a bad `decisions`, `decisions.batch` or `decisions.nitsNeedDecision`;
  - a bad `planning`, `planning.preflightReviewers` or entry (an entry needs a non-empty string `agent` with no control characters and no spaces at either end, and a `when` must be a non-empty list of path prefixes); a bad entry is dropped on its own. A `"when": null` and a key other than `agent`, `when` and `$comment` are reported too, but the entry is kept, and with a null `when` it runs on every plan;
  - a bad `governance.trustedWritePaths`: a bad entry is dropped, and a value that isn't a list counts as an empty list, so no path is trusted (not the defaults);
  - a bad `governance.allowlist` (the list or an entry);
  - an unknown `governance.planEdits` value, which then counts as `"ask"`, so every plan edit prompts.
- **Advisory problems warn once per change.** The first time a given set of advisory problems is seen, the guard writes one `"decision": "warn"` entry to the governance log and shows a message beside the action's own decision. It warns again only when the set changes; fixing every problem and later reintroducing one warns again, also when it was fixed while an escalating problem was present. A `trustedWritePaths` entry quoted in the message is cut to 60 characters. The message names as many problems as fit in 1000 characters and then says how many more there are; the log entry names them all.
- **The after-Bash check uses the same split.** It reads the config only after a Bash call that changed a workflow file. It then logs advisory problems once as `warn`, sharing the guard's record of what was shown, and logs an escalating problem as `error` each time.
- **Where it is remembered.** The set already shown is kept as a hash in `$TMP/usiatech-governance/{project}/config-warned`, which no trusted write path may name. It is recorded only after the `warn` entry is in the log; a warning that couldn't be logged is shown again. If that file can't be read, isn't a small regular file, or its folder can't be trusted (see the after-Bash check above), the warning is shown again. If it can't be written, or can't be removed once the problems are fixed (it is removed only from a folder that can be trusted), that is logged as `error` and the action's decision is still unchanged. If that `error` entry can't be logged either, it is shown as a message.

**Trusted writes** (ESP-9). Some writes carry no risk, so the guard doesn't ask for them. It still logs each one as `"decision": "trusted"`, and `governance-reviewer` lists them all.
- **`governance.trustedWritePaths`**: writes outside the project folder that go through. The default is:
  - `$TMP/claude/{project}/**`, the session scratchpad;
  - `~/.claude/projects/{project}/memory/**`;
  - `~/.claude/session-data/**`.

  `$TMP` is the OS temp folder and `~` the home folder. `{project}` is the project folder as Claude Code names it: each character other than `A-Z`, `a-z` or `0-9` becomes `-`, so `c:\Users\me\src\app` becomes `c--Users-me-src-app`. Memory and the scratchpad are trusted for the current project only, because memory is loaded into later sessions as instructions.
  - A repo list replaces the default, and `[]` makes every outside write ask again.
  - An entry must start with `$TMP/` and name a folder below it, start with `~/.claude/projects/` and name a folder below it, or start with `~/.claude/session-data/`. Any other entry (`~/.claude/**`, `~/.ssh/**`, `$TMP/**`, an absolute path) is a config problem. So is an entry with `\` or `:`, or with a folder name that is empty or ends in `.` or a space (`$TMP/./**`, `$TMP//**`). So is any entry in `$TMP/usiatech-governance` (any case), where the after-Bash workflow check keeps its snapshots: trusting it would let Claude rewrite a snapshot without a prompt and hide a workflow change (ESP-21).
  - Inside a trusted folder these still ask: `settings.json`, `settings.local.json`, `.mcp.json`, `.claude.json`, `CLAUDE.md`, `AGENTS.md`, and anything under a `.git`, `hooks`, `plugins` or `.ssh` folder. So does any name with `:` or ending in `.` or a space, since Windows reads `settings.json.` and `settings.json::$DATA` as `settings.json`, a Windows device name (`CON`, `NUL`, `COM1`…), and an existing file with more than one hard link.
  - The target is compared by its real path, after following links from the nearest existing folder. A trusted folder that is itself a link to somewhere else is not trusted, and neither is a link to a missing target. If the real path can't be worked out, the write asks.
  - If the guard can't log a trusted write to `.claude/governance-log.jsonl`, the write asks instead, since the log is its only record.
  - Env files and secrets are refused there as they are anywhere.
  - If Claude Code keeps its scratchpad somewhere other than `$TMP/claude/{project}` on your system, add that folder to the list.
- **`governance.planEdits`**, `"allow"` (default), `"ask"` or `"all"`. With `"allow"`, an edit to an existing `.claude/plans/active.md` goes through when the only changes are:
  - lines in the Change log;
  - the `[ ]`/`[x]` state of lines under Tasks;
  - `Evidence:` bullets (and the lines indented under them) in the Acceptance criteria section.

  Anything else asks: a change to Files, AC text, task text or a heading, a new plan, or an edit whose result can't be worked out. `"ask"` keeps the 0.5.1 behaviour, where every plan edit asks.

  `"all"` trusts every Write, Edit or MultiEdit of `.claude/plans/active.md` and of any file under `.claude/plans/archive/`, including creating or replacing the plan and changing its Files, ACs or tasks. Each one is logged as `"decision": "trusted"`. Env files, secrets and `protectedPaths` are still refused or asked about, and plan files written or moved through Bash are checked as before. **Trade-off:** Claude can then widen its own scope without a prompt, so the governance-reviewer's check becomes the only scope check on plan changes. It flags any Files entry, AC or task added after approval without a dated Change log line. Set the value back to `"allow"` to restore the prompt.

These keys only stop the guard's prompt. Claude Code still asks before writing outside the folders it was started with. To stop that prompt too, add matching rules to your user `~/.claude/settings.json`, using the real folder names:

```json
{ "permissions": { "allow": [
  "Edit(//c/Users/<you>/AppData/Local/Temp/claude/**)",
  "Edit(~/.claude/projects/<project>/memory/**)",
  "Edit(~/.claude/session-data/**)"
] } }
```

The guard fails open on internal errors, so a bug can't lock a session. Each failure is logged as `"decision": "error"` in `governance-log.jsonl` and printed to stderr, and the reviewer reports these entries. `ask` depends on Claude Code's permission prompt: in a fully auto-approved session, rely on `deny` rules and the reviewer.

## Keeping sessions cheap
Most of a long session's cost is text that tools put into the conversation: test output, logs, API responses. Three habits keep it down:
- Send large command output to a file and print only a summary (the counts, the failing lines). The gate runner already works this way: one line per step, with the full output in a log file.
- Ask Jira, or any API, for only the fields you need. A Jira search with the default fields can return tens of thousands of characters; `summary`, `status`, `priority` and `labels` are usually enough.
- Use the context-mode plugin to process output when it is installed: the raw output stays in its sandbox and only the derived answer comes back. The plugin doesn't depend on it; without it, a small script that reads the saved file does the same job.

## Checking for duplicate installs
Two installs of this plugin can be active in one repo, for example an old project-scope install next to a newer user-scope one. It is then unclear which guard runs. After an upgrade, run `claude plugin list` in each repo that uses the plugin and look at the `usiatech-engineering` entries:
- **More than one `usiatech-engineering@usiatech` entry:** one is usually an older version with `Scope: project`. Remove it from that repo with `claude plugin uninstall usiatech-engineering@usiatech --scope project`, run in the repo's folder. This edits the repo's `.claude/settings.json`, so commit that change. That file is shared: once the entry is gone, the repo no longer enables the plugin for other people who work in it, so check first that each of them has a user-scope install, or they lose the guard without any warning. Keep the project-scope install only if the repo is meant to pin its own version.
- **A `usiatech-engineering@synced` warning:** a copy synced from claude.ai has the same name. The local install takes precedence and the synced copy is not loaded. Remove the synced copy in claude.ai to clear the warning.
