# Plan: Guard — Windows path tricks and after-Bash workflow check (ESP-6)

## Goal
Close the two remaining guard enforcement gaps from the workflow-checks-hardening spec: workflow files written by a Bash command are checked with the workflow rules right after the command (R6), and Windows path variants of a workflow file (`x.yml.`, `x.yml `, `x.yml::$DATA`, `x.yml:stream`) are recognised as workflow paths (R7).

## Requirement references
- Spec `docs/specs/2026-10-02-workflow-checks-hardening.md` (Status: approved): R6, R7; AC6, AC7, AC14; Constraints (R6 PostToolUse hook, < 100 ms, no ADR); Open question on sticky block (deferred, not in this plan)
- Ticket #47 = Jira ESP-6 (blocks ESP-7 / #48)

## Acceptance criteria
- AC6 (spec AC6, R6): A test runs the after-Bash hook on a temp repo. Writing a high-risk workflow via a shell command (heredoc, and `cp` of a fixture) produces hook output naming the rule ID and the file, and a `decision: "finding"` entry in `.claude/governance-log.jsonl`. A command that writes a high-risk workflow and then exits non-zero (`PostToolUseFailure`) gives the same output and entry. A Bash command that changes no workflow file produces no output and no workflow log entry. A workflow committed or staged by the command without changing the files on disk (`git update-index --cacheinfo` + `git commit` + `git checkout --`; a commit on another branch; a staged-only change) gives the same output and entry; a commit that touches no workflow gives none. On a repo with 20 workflow files and no git, the no-change run — snapshot step plus after-hook together — takes under 100 ms timed inside the test process (median of 10 runs); in a git repo the no-change run makes exactly 4 git calls (counted, not timed), and the spawned hook loads none of `governance-policy.mjs`, `governance-rules.mjs` or `workflow-rules.mjs` (shown by `NODE_DEBUG=esm`, with a changed-workflow run as the positive control; changed 2026-10-07). Snapshots are left neither after a normal run nor after a failed one, and stale ones (older than 10 minutes) are removed. A snapshot holding a ref or index id like `--output=<path>`, or one that isn't JSON, is logged as not valid, git writes no file, and the HEAD fallback runs; a snapshot folder that is a link, or (POSIX) owned by another user or writable by group or others, is refused and logged (fix set D, added 2026-10-07).

Non-workflow decisions for these names are unchanged. `Write` to `package.json.` / `package.json::$DATA` with a risky dependency change gets the dependency findings on win32 and not on POSIX.
